# Удалённый бэкап по SSH

Как бэкапить панель или бота, которые стоят на **другом сервере** — там, где сам `lazarus` не установлен. Дамп базы и архив файлов делаются на удалённом сервере и **стримятся** по SSH на этот хост, где и шифруются. На удалённый диск ничего лишнего не пишется.

Удалённая цель настраивается через мастер **Цель бэкапа** (Настройки → пункт 7): для панели или бота выбираете «на другом сервере (по SSH)» и вводите хост/порт/пользователя/ключ.

> Восстановление удалённой цели из этого меню **не поддерживается** — restore делается на самом сервере цели (см. [ограничение](#ограничение-restore-не-для-удалённой-цели) ниже).

---

## TL;DR — 3 шага для новичка

1. На сервере, где стоит `lazarus`, откройте **Настройки → 7. Цель бэкапа**.
2. Выберите **что бэкапить** (панель / бот / оба) и на шаге «где находится» — **«2. На другом сервере (подключимся по SSH)»**. Введите IP, порт, пользователя и путь к SSH-ключу.
3. Мастер проверит SSH-связь. Если связь установлена — сохраните и запустите обычный бэкап (главное меню → пункт 1). Архив ляжет в `BACKUP_DIR` **этого** сервера, S3/Telegram — как для локальных бэкапов.

---

## Когда это нужно

- Панель или бот стоят на сервере, куда вы **не хотите ставить** `lazarus` (нет места, чужой/managed хост, минимальный образ).
- Хотите держать **все бэкапы централизованно** на одной машине-бэкапере, а не по одному агенту на каждом сервере.
- Нужен «внешний» бэкап-хост, физически отдельный от продакшена (off-site).

Если панель/бот **на этом же сервере**, где стоит `lazarus`, удалённая цель не нужна — используйте обычный [локальный бэкап](backup.md).

Если задача — **переехать** панелью на новый сервер (а не просто бэкапить), это отдельная команда `lazarus migrate panel` — см. [Перенос панели](panel-migration.md).

---

## Как это работает

- **Pull, а не push** — команда запускается на этом (бэкап) хосте и сама тянет данные с удалённого сервера по SSH.
- **Источник read-only** — на удалённом сервере выполняются только `docker exec … pg_dump` (дамп БД) и `tar` (файлы каталога). Ничего не меняется, не останавливается, не удаляется.
- **Plaintext не пишется на удалённый диск** — дамп и tar идут потоком по шифрованному SSH-каналу, а сжатие и шифрование архива происходят **только локально**, на этом хосте.
- **Архив байт-совместим с локальным** — те же внутренние имена файлов, что и у обычного бэкапа. Разница только в том, где взяты данные.
- **Per-target независимо** — панель и бот могут быть в разных местах: например, панель удалённо по SSH, а бот локально (или наоборот).

Что попадает в удалённый архив панели: дамп БД + роли кластера (globals) + дамп `infra-billing` (если сайдкар активен на удалённом). Для бота: дамп БД бота + KB-сайдкар при наличии.

## Настройка через мастер «Цель бэкапа»

Откройте **Настройки → 7. Цель бэкапа**. Мастер из двух шагов.

**Шаг 1/2 — что бэкапить:**

```
Шаг 1/2 — что бэкапить:
 1. Панель Remnawave
 2. Бот магазина (Telegram)
 3. Панель + бот   — оба архива за один запуск, папка: /opt/lazarus-backups
 0. Назад
```

**Шаг 2/2 — где находится цель.** Для каждой выбранной цели мастер спросит её расположение:

```
Шаг 2/2 — где находится: Панель (Remnawave)?
  1. На этом сервере       (локально — найдём автоматически)
  2. На другом сервере     (подключимся по SSH)
  Выбор (1/2, Enter = 1): 2
  Хост (IP или user@host): 203.0.113.10
  SSH-порт (Enter = 22): 22
  Пользователь (Enter = root): root
  Ключ: путь к файлу, либо вставьте ключ целиком (Enter = /root/.ssh/id_ed25519):
  Каталог панели на удалённом (Enter = /opt/remnawave): /opt/remnawave
  Контейнер БД (Enter = remnawave-db): remnawave-db
```

Для **бота** вопросы аналогичны, но спрашивается каталог бота (Enter = `/opt/private-remnawave-telegram-shop-bot`) и контейнер БД бота (Enter = `rwp_shop_db`).

После ввода мастер сразу **проверяет связь**:

```
[SUCCESS] SSH-связь с 203.0.113.10 установлена.
```

Если связь не поднялась — конфиг всё равно сохранится, но с предупреждением: бэкап этой цели работать не будет, пока не почините ключ/порт/хост/доступ:

```
[WARN] SSH-связь с 203.0.113.10 НЕ установлена (ключ/порт/хост/доступ?).
[WARN]   Конфиг сохранён, но бэкап этой цели НЕ будет работать, пока связь не починена.
```

### Как задать SSH-ключ

В поле «Ключ» можно:
- указать **путь** к приватному ключу (`/root/.ssh/id_ed25519`);
- **вставить ключ целиком** прямо в терминал — он сохранится в постоянный файл `0600` в каталоге установки (конфиг ссылается на путь между запусками);
- оставить пустым (Enter) — будет использован найденный дефолтный ключ (`~/.ssh/id_ed25519`, `id_rsa` и т.п.).

Требования на удалённой стороне: работающий `docker` и запущенный контейнер БД. Ключ должен пускать без пароля (BatchMode).

## Что пишется в config.env

Мастер сохраняет параметры в `config.env`. Тот же результат можно задать вручную:

```bash
# --- Панель на другом сервере (по SSH) ---
PANEL_TRANSPORT="ssh"
PANEL_SSH_HOST="203.0.113.10"      # хост или user@host
PANEL_SSH_PORT="22"
PANEL_SSH_USER="root"
PANEL_SSH_KEY="/root/.ssh/id_ed25519"
PANEL_PATH="/opt/remnawave"        # каталог панели НА УДАЛЁННОМ сервере
PANEL_DB_CONTAINER="remnawave-db"

# --- Бот на другом сервере (по SSH) ---
BOT_TRANSPORT="ssh"
BOT_SSH_HOST="203.0.113.20"
BOT_SSH_PORT="22"
BOT_SSH_USER="root"
BOT_SSH_KEY="/root/.ssh/id_ed25519"
```

| Ключ | Default | Назначение |
|---|---|---|
| `PANEL_TRANSPORT` / `BOT_TRANSPORT` | `local` | `local` \| `ssh` — где находится цель |
| `PANEL_SSH_HOST` / `BOT_SSH_HOST` | — | хост или `user@host` удалённого сервера |
| `PANEL_SSH_PORT` / `BOT_SSH_PORT` | `22` | SSH-порт |
| `PANEL_SSH_USER` / `BOT_SSH_USER` | `root` | SSH-пользователь |
| `PANEL_SSH_KEY` / `BOT_SSH_KEY` | — | путь к приватному ключу |

Полный список ключей — [../CONFIG_REFERENCE.md](../CONFIG_REFERENCE.md), раздел «Удалённая цель (SSH)».

## Запуск бэкапа

После настройки удалённая цель работает как обычная: запускайте бэкап из главного меню (пункт 1) или по расписанию. Внешне ничего не меняется — только вместо локального `pg_dump`/`tar` данные тянутся по SSH:

```
[INFO] Удалённый дамп БД (remnawave-db, db=postgres)...
```

Если транспорт `ssh`, но SSH-хост не задан, бэкап **не выполнится** (явный отказ, без тихого падения в локальный путь):

```
[ERROR] Транспорт цели = ssh, но SSH-хост не задан — бэкап НЕ выполнен (Настройки → Цель бэкапа).
```

## Ограничение: restore не для удалённой цели

**Восстановление удалённой (SSH) цели из меню `lazarus` не поддерживается.** Причина техническая: restore запускает `docker`-команды локально — для удалённой цели они ударили бы по **локальному** docker-демону, а не по нужному серверу (восстановление не в ту БД).

При попытке восстановить SSH-цель:

```
[ERROR] Восстановление удалённой цели (SSH) не поддерживается из этого меню.
Тянутый архив восстанавливайте на самом удалённом сервере или по runbook'у —
иначе docker-команды ударят по ЛОКАЛЬНОМУ демону (не та БД).
```

**Как восстановить удалённую цель:** скопируйте нужный архив на сам сервер цели, поставьте туда `lazarus` (или разверните вручную) и восстановите **локально** на этом сервере — тогда `docker`-команды пойдут в правильный демон. Общая процедура — [Восстановление из бэкапа](restore.md).

## Частые проблемы

| Симптом | Причина / решение |
|---|---|
| `SSH-связь … НЕ установлена` | Ключ/порт/хост/доступ. Проверьте вручную: `ssh -p ПОРТ -i КЛЮЧ user@host true`. Ключ должен пускать без пароля. |
| `Удалённая БД не готова (pg_isready)` | Контейнер БД на удалённом не запущен или имя контейнера не то. Проверьте `PANEL_DB_CONTAINER` / контейнер бота. |
| `Транспорт цели = ssh, но SSH-хост не задан` | Не заполнен `PANEL_SSH_HOST` / `BOT_SSH_HOST`. Пройдите мастер «Цель бэкапа» заново. |
| Нужно восстановить удалённую цель | Из меню нельзя — делайте restore на самом сервере цели (см. ограничение выше). |
