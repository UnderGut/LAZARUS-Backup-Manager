# Диагностика и частые проблемы

Инструменты `lazarus` для самодиагностики и таблица типовых сбоев с решениями.

Если что-то пошло не так — не гадайте. У lazarus есть четыре read-only команды, которые за секунды показывают состояние системы, целостность архивов и что именно пропустил последний бэкап. Начните с них, потом сверьтесь с таблицей ниже.

---

## TL;DR — куда смотреть при проблеме

1. **`lazarus diag`** — полный снимок системы одной командой (версии, зависимости, цель, контейнеры, диск, cron, бэкапы, ошибки из лога). С этого начинают.
2. **`lazarus stacks`** — что lazarus реально нашёл на сервере (панель / бот / infra-billing) и совпадает ли это с конфигом. Первый шаг, если «контейнер БД не найден».
3. **`lazarus verify`** — проверка целостности всех архивов (битые файлы всплывут сразу).
4. **`lazarus skipped`** — что не вошло в последний бэкап и почему.
5. **`lazarus --debug <команда>`** — подробный лог по категориям, когда нужно понять, где именно застряло.

Лог всегда пишется в **`/var/log/lazarus_backup.log`** — туда смотрят, когда команда уже отработала.

## Инструменты диагностики

### `lazarus stacks` — что нашлось на сервере

Одно сканирование `docker ps -a`. Показывает обнаруженные стеки **по образам и compose-проектам, независимо от конфига**, и подсвечивает расхождения «конфиг ↔ реальность» (не правит, только показывает):

```
lazarus stacks
```

```
Обнаруженные стеки:
  Панель:        /opt/remnawave  app=remnawave  db=remnawave-db
  infra-billing: app=—  db=—
  Бот:           —  app=—  db=—

Конфиг (активная цель panel): path=/opt/remnawave db=remnawave-db
```

Если конфиг указывает на одно имя контейнера БД, а обнаружено другое — появится жёлтое предупреждение:

```
  ⚠ Конфиг БД панели ('remnawave_db') ≠ обнаруженной ('remnawave-db')
```

Это главный инструмент, когда бэкап падает с «контейнер БД не найден»: сначала смотрят, что видит `stacks`, потом чинят конфиг под реальность.

### `lazarus diag` — снимок системы

Одна команда — полный snapshot состояния для troubleshooting. Ничего не меняет. Секреты **не выводит** (пароль/токен/ключи показаны как `set / not set`, без значений):

```
lazarus diag                 # вывод в терминал
lazarus diag > diag.txt      # сохранить в файл, чтобы приложить к отчёту
```

Что в отчёте:

| Секция | Что показывает |
|---|---|
| `VERSIONS` | версия скрипта, bash, openssl, docker, ОС, ядро |
| `DEPENDENCIES` | наличие `curl/wget/gzip/zstd/tar/openssl/docker/aws/timeout/shred/python3/jq` (✓/✗) |
| `TARGET` | режим и цель (панель / бот / both), расположение, префикс, состояние infra-billing |
| `CONTAINER STATUS` | статус контейнеров БД и приложения + health |
| `PANEL/BOT CONFIG` | путь, существует ли, compose-файл, `.env` |
| `BACKUPS` | каталог, число архивов, формат (v2 с HMAC / v1 legacy / без шифрования), последний |
| `DISK` | точка монтирования, всего/занято/свободно, пороги WARN/CRITICAL |
| `CRON` | расписание full/db/files + последний запуск |
| `SECURITY` | задан ли `BACKUP_PASSWORD` (да/нет, без значения) |
| `REMOTE STORAGE` | тип, bucket/endpoint (маскирован), заданы ли ключи |
| `TELEGRAM` | заданы ли токен и chat id (да/нет), включены ли уведомления |
| `TIMEOUTS` | таймауты pg_dump/tar/encrypt/restore |
| `RECENT ERRORS` | последние 10 строк `[ERROR]` из лога + число ошибок за 24ч |
| `LOG ROTATION` | logrotate и размер текущего лога |

Именно `diag` прикладывают к любому вопросу по проблеме — в нём сразу видно 90% причин.

### `lazarus verify` — целостность всех архивов

Проверяет **каждый** архив в каталоге бэкапов. Для зашифрованных v2 — сверяет HMAC (детект corruption или неверного пароля), затем расшифровывает и проверяет сам архив (`gzip -t` / zstd). Для incremental — дополнительно проверяет, что базовый full на месте (иначе inc — «сирота»):

```
lazarus verify
```

```
[1/4] lazarus_panel_full_20260718_040001.tar.gz.enc ... OK
[2/4] lazarus_panel_db_20260717_040001.tar.gz.enc ... OK
[3/4] lazarus_inc_20260718_120001.tar.gz.enc ... FAIL (orphan inc (base full not found))
[4/4] lazarus_panel_full_20260710_040001.tar.gz ... OK

OK: 3 / FAIL: 1 / SKIP: 0 / Всего: 4 (за 6с)
```

Важные нюансы:

- **SKIP (no password)** — зашифрованные архивы пропущены, потому что `BACKUP_PASSWORD` не задан. Проверка **неполная** — задайте пароль в `config.env` для полной верификации.
- **FAIL** отправляет **CRITICAL-алерт в Telegram** со списком битых файлов (плохие новости не молчат). Положительный отчёт шлётся только с флагом `--report-tg`.
- Идеально ставить в cron раз в неделю — раннее обнаружение bit-rot:
  ```
  0 4 * * 0 /usr/local/bin/lazarus --report-tg verify >> /var/log/lazarus_backup.log 2>&1
  ```

### `lazarus skipped` — что не вошло в бэкап

Полный отчёт о файлах, которые последний бэкап **пропустил** (например, слишком большие, сокеты, недоступные по правам). Группирует по причине, сортирует по размеру:

```
lazarus skipped
```

```
━━━ Пропущенные файлы (последний бэкап) ━━━
Архив:    lazarus_panel_full_20260718_040001.tar.gz.enc
Дата:     2026-07-18 04:00:12
Файлов:   2

Общий вес пропущенных: 3.1G

[превышен MAX_FILE_SIZE_MB]
   2.4G  /opt/remnawave/logs/access.log
   0.7G  /opt/remnawave/logs/old.log.1
```

Если всё вошло — покажет `✓ Все файлы вошли в архив. Пропущенных нет.` В интерактиве листается через `less` (стрелки / `q` — выход); при `lazarus skipped > file.txt` просто печатает.

## Режим отладки (`--debug`)

Флаг `--debug` (или `-d`) включает подробное логирование **на stderr** для любой команды. Ставится **перед** командой:

```
lazarus --debug backup create
lazarus --debug verify
lazarus --debug migrate panel
```

В debug-режиме:

- каждая строка помечена временем и **категорией**: `[LOCK]`, `[TG]`, `[ENC]`, `[HMAC]`, `[TIMEOUT]`, `[MIGRATE]`, `[VERIFY]`, `[INSTALL]`, `[CATEGORY]` и др. — по ним видно, на каком этапе застряло;
- очистка экрана в меню отключена (виден весь скролл);
- debug-строки идут в stderr, поэтому не портят вывод команд вида `x=$(lazarus ...)`.

Пример: если бэкап молча не отдаёт архив в Telegram — `lazarus --debug backup create` покажет строки `[TG]` с реальной причиной (неверный токен, chat id, размер файла).

## Где лог

- **Файл:** `/var/log/lazarus_backup.log` — сюда пишутся `INFO`/`WARN`/`ERROR` всех запусков (в т.ч. cron).
- Последние ошибки удобно смотреть через `diag` (секция `RECENT ERRORS`) или напрямую:
  ```
  grep '\[ERROR\]' /var/log/lazarus_backup.log | tail -20
  ```
- **Ротация:** системный `logrotate` (`/etc/logrotate.d/lazarus`), либо встроенная — `diag` покажет, какая активна, и текущий размер файла.

### flock — «другой процесс уже запущен»

Чтобы cron-бэкап и ручной запуск не топтали одни и те же файлы, lazarus держит **advisory-lock** (`flock`) на `/var/run/lazarus_backup.lock`. Если увидели:

```
Другой процесс бэкапа уже запущен (PID: 12345). Повторите позже.
```

— значит, параллельно уже идёт бэкап (обычно cron). Это **не ошибка**, а защита. Дождитесь окончания или проверьте `ps -p 12345`. Lock-файл специально **не удаляется** после работы (это устранило race при параллельных запусках) — эксклюзивность держит сам `flock`, а не наличие файла, так что удалять его вручную не нужно.

## Таблица частых проблем

| Симптом | Причина / решение |
|---|---|
| **«Контейнер БД не найден»** при бэкапе | Имя контейнера в конфиге не совпадает с реальным. Запустите `lazarus stacks` — он покажет обнаруженное имя и подсветит расхождение. Приведите `DB_CONTAINER_NAME` (или `PANEL_DB_CONTAINER`) в `config.env` к тому, что нашлось, и повторите. |
| **«Мало места»** / бэкап падает на архивации | На диске нет места под архив + распаковку. Проверьте `lazarus diag` → секция `DISK` (свободно / пороги). Освободите место, удалите старые бэкапы (`lazarus cleanup`) или временно перенесите `BACKUP_DIR` на больший том. |
| **Нет `zstd`** (`zstd ✗` в diag) | Выбрано `COMPRESSION=zstd`, но пакет не установлен → бэкап падает или откатывается на gzip. Поставьте: `apt install zstd` (или `dnf install zstd`). Старые архивы читаются автоматически по magic-байтам — совместимость не ломается. |
| **SSH-цель не бэкапится** (удалённый сервер) | 1) Проверьте `lazarus diag` — в `TARGET` должно быть `Note: цель удалённая (SSH)`. 2) Убедитесь, что SSH до цели работает и порт верный (по умолчанию `22`). 3) `docker`/`path` в diag относятся к **локальному** хосту, не к удалённой цели — проверяйте контейнеры на самой цели вручную. 4) Прогоните с `lazarus --debug backup create` и смотрите категорию логов на этапе подключения. |
| **Уведомления в Telegram не приходят** | `lazarus diag` → секция `TELEGRAM`: `Token` и `Chat ID` должны быть `✓ set`, `Notifications` — включены. Если один из них `✗` — задайте `BOT_TOKEN` / `CHAT_ID` в `config.env`. Токен берётся у `@BotFather`, chat id — числовой (для группы с минусом). Проверьте причину доставки: `lazarus --debug backup create` и смотрите строки `[TG]`. |
| **`verify` показывает SKIP, а не OK** | Зашифрованные архивы пропущены — не задан `BACKUP_PASSWORD`. Проверка неполная. Задайте пароль в `config.env` и повторите `lazarus verify`. |
| **`verify` → FAIL «orphan inc»** | У incremental-архива нет базового full (удалён ротацией или вручную). Сам inc бесполезен без базы — удалите его или восстановите базовый full. |
| **Много файлов пропущено** | `lazarus skipped` покажет причину по группам. Частая — превышен `MAX_FILE_SIZE_MB` (логи, дампы). Либо поднимите лимит в `config.env`, либо исключите каталог логов из бэкапа. |
| **Команда молча висит / не завершается** | Прогоните с `--debug` — по последней категории (`[TIMEOUT]`, `[ENC]`, `[TG]`) видно, где застряло. Проверьте таймауты в `diag` → секция `TIMEOUTS`. |
