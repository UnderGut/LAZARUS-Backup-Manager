# Восстановление из бэкапа

Как вернуть Remnawave Panel (или бота) из ранее созданного бэкапа с помощью `lazarus restore`.

Восстановление — **необратимая** операция: текущие данные цели заменяются данными из архива. LAZARUS выстраивает безопасный порядок (сначала снимает snapshot живой БД, потом разрушает) и умеет **автоматически откатиться**, если импорт провалится. Восстановление работает **только для ЛОКАЛЬНОЙ цели** — для удалённой (SSH) цели restore недоступен из меню.

---

## TL;DR — 3 шага для новичка

1. Запустите меню и выберите восстановление:
   ```bash
   lazarus restore
   ```
2. Выберите **тип** (Полный / Только БД / Только файлы / Инкрементальный) и **файл** из списка (можно отфильтровать по дате).
3. Пройдите подтверждения (`RESTORE` → при необходимости `DELETE` → `DROP`). LAZARUS сам снимет точку отката, остановит контейнеры, восстановит данные и поднимет стек обратно.

> Если что-то пойдёт не так на импорте БД — LAZARUS **сам откатит** базу из snapshot живой БД и поднимет контейнеры. Бот/панель не останутся выключенными.

---

## Запуск

Два равнозначных способа:

```bash
lazarus restore          # сразу меню восстановления
```

или из интерактивного меню:

```
lazarus                  # главное меню → «Восстановить»
```

Если у вас **обе** цели (панель + бот на одном сервере), сначала спросят, **какую цель** восстанавливать:

```
Восстановление — какую цель?

 1. Remnawave Panel — этот сервер
 2. Telegram-бот — этот сервер
 0. Назад
```

SSH-цель в этом списке будет серой с пометкой «по SSH восстановление недоступно» — восстановить её можно только запустив `lazarus` на самом сервере цели (или переключив цель на «этот сервер» в Настройках).

---

## Выбор типа и файла

После выбора цели — меню типов. В скобках — сколько файлов каждого типа найдено:

```
Восстановление из бэкапа
Цель: Remnawave Panel · этот сервер · контейнер БД remnawave-db
Восстановление заменит текущие данные этой цели.

 1. Полный бэкап        [12 шт]
 2. Только БД           [30 шт]
 3. Только файлы        [8 шт]
 4. Инкрементальный     [5 шт] — восстановит всё: последний полный + изменения
 0. Назад
```

| Тип | Что восстанавливает |
|---|---|
| **Полный** | база данных + файлы каталога (compose, `.env`, сертификаты, nginx) |
| **Только БД** | только дамп базы; файлы не трогаются |
| **Только файлы** | только каталог; база не трогается |
| **Инкрементальный** | автоматически подтягивает **базовый полный** бэкап + изменения и разворачивает как полный |

### Список файлов и фильтр по дате

Дальше — список бэкапов (по умолчанию 5 последних, самые свежие сверху):

```
Восстановление: Полные бэкапы
Всего файлов: 12

     дата время  | размер | версия бота
  1. 25.12 03:00 |  142M | [шифр] [v6.0.0]
  2. 24.12 03:00 |  141M | [v6.0.0]
  ...
 777. Фильтр по дате   ·   888. Показать все (12 шт)   ·   999. Имена файлов
 0. Назад
```

Служебные хоткеи:
- **777** — фильтр по дате (или сброс, если фильтр уже активен).
- **888** — показать все файлы / свернуть до 5.
- **999** — переключить отображение (дата+размер ↔ полные имена файлов).

Фильтр по дате (пункт **777**) принимает несколько форматов:

| Ввод | Значение |
|---|---|
| `25.12` | все файлы за 25 декабря (любой год) |
| `25.12.2026` | конкретная дата |
| `25/12` | синоним `25.12` (слэш) |
| `2026-12-25` | ISO-формат |

Если за указанную дату файлов нет — фильтр сбрасывается (не выходя из списка). Метка `[шифр]` означает зашифрованный архив (при восстановлении спросят пароль). Метка версии жёлтая, если версия бэкапа не совпадает с установленной — это **предупреждение, не ошибка**, restore возможен.

## Что происходит при восстановлении (безопасный порядок)

LAZARUS выполняет разрушительные шаги **только после** того, как гарантирует возможность отката. Порядок для **полного** восстановления:

1. **Пароль** (для `.enc`-архивов) — до 3 попыток; проверка HMAC (формат v2) или gzip (legacy v1).
2. **Гард идентичности** — проверка, что путь и контейнеры цели указывают на **свой** стек (бот ≠ панель ≠ billing). Неизвестная роль = отказ до любых действий.
3. **Конфликт-гард версий** — если `docker-compose` в архиве **отличается** от установленного (типовой случай: свежая панель + старый архив), спросят, что делать:
   - только **ДАННЫЕ (база)** — файлы не трогаем (рекомендуется после свежей установки);
   - файлы из архива, но **сохранить** текущие `docker-compose`/`.env`;
   - вернуть **ВСЁ как есть** (точная копия старого сервера; живые compose/.env заранее копируются в `infra_replaced_*`).
4. **Валидация нового дампа** — новый дамп БД проверяется (целостность + размер) **до** разрушения текущей базы.
5. **Snapshot живой БД** — снимок текущей базы (`pre_restore_snapshot_*.sql.gz`) как **точка отката**. Если снять не удалось — в интерактиве попросят ввести `PROCEED`, иначе restore прерывается (без `--i-know-what-i-am-doing` в неинтерактиве — отказ).
6. **Остановка контейнеров** — `docker compose down` (rc проверяется; провал = прерывание до rsync).
7. **Синхронизация файлов** — rsync из архива (провал = прерывание до разрушения БД, контейнеры поднимаются обратно).
8. **Удаление volume БД** (опционально, с подтверждением `DELETE`) — для «чистого» восстановления с нуля.
9. **DROP SCHEMA + импорт** — `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`, затем импорт дампа с `ON_ERROR_STOP=1`.
10. **Авто-откат при провале** — если импорт упал, база откатывается из snapshot (шаг 5), контейнеры поднимаются. Бот/панель не остаются offline.
11. **Импорт сайдкаров** (для панели) — роли/глобалы (`globals`), при наличии — infra-billing (отдельное подтверждение и своя точка отката); для бота — KB ИИ-саппорта.
12. **Подъём стека** — `docker compose up -d` (свежий пул соединений).

Для **db_only** файловый коридор пропускается: приложение останавливается (`compose stop`), контейнер БД остаётся поднятым для импорта, затем весь стек поднимается заново — чтобы приложение подхватило новую БД свежим пулом.

## Слова-подтверждения и авто-отмена

Разрушительные шаги требуют ввода **точного слова** (регистр важен). У каждого — **авто-отмена через 60 секунд**, если оператор отвлёкся:

| Слово | Когда спрашивается |
|---|---|
| `RESTORE` | подтверждение цели восстановления (путь) |
| `DELETE` | удаление Docker volume БД (только если вы согласились его удалять) |
| `DROP` | очистка схемы БД (`DROP SCHEMA public CASCADE`) перед импортом |

Ввели не то слово или истекли 60 секунд — операция отменяется:

```
Введите RESTORE для подтверждения: RESTORE
...
Введите DROP для подтверждения:
Таймаут (60с) — операция автоматически отменена для безопасности
```

Ctrl+C в деструктивном коридоре (после `down`) требует **двойного** нажатия — чтобы rsync/volume/DROP не оборвались на полпути.

## Неинтерактивный режим (скрипты / cron)

Меню восстановления рассчитано на оператора. Для автоматического восстановления нужны **явные** флаги — по умолчанию всё безопасно и restore откажется работать без них:

```bash
lazarus --yes --i-know-what-i-am-doing --restore-drop-schema restore
```

| Флаг | Назначение |
|---|---|
| `--yes` (`-y`) | автоподтверждение |
| `--i-know-what-i-am-doing` | разрешить деструктивные операции (обязателен для restore без TTY) |
| `--restore-drop-schema` | выполнить `DROP SCHEMA` перед импортом (иначе импорт может упасть на существующих таблицах) |
| `--restore-drop-volume` | удалить Docker volume БД (полностью чистое восстановление) |
| `--restore-include-env` | восстановить `.env` из архива (по умолчанию исключается ради защиты секретов) |

Без `--i-know-what-i-am-doing` вместе с `--yes` restore выдаст ошибку:

```
Restore требует подтверждения. Используйте --i-know-what-i-am-doing вместе с --yes
```

> `--dry-run` для restore выполняет предпросмотр (план rsync, проверки) и пропускает разрушительные шаги — ничего не меняется.

## Только для локальной цели

Восстановление выполняет `docker exec`, `docker volume rm`, `DROP SCHEMA` **локально**. Для удалённой (SSH) цели это ударило бы по **локальному** docker (не та БД) — поэтому restore для SSH-цели **заблокирован**:

```
Восстановление недоступно для удалённой (SSH) цели.
Запустите lazarus на сервере самой цели, либо переключите её на 'этот сервер' (Настройки → Цель бэкапа).
```

Чтобы восстановить удалённый сервер — запустите `lazarus restore` **на самом этом сервере**, либо перенесите архив и разворачивайте по runbook'у аварийного восстановления.

## Частые проблемы

| Симптом | Причина / решение |
|---|---|
| «Restore требует подтверждения» | В неинтерактиве не хватает флагов. Добавьте `--yes --i-know-what-i-am-doing` (и `--restore-drop-schema` для импорта в непустую БД). |
| «Не удалось снять snapshot живой БД» | Текущая БД недоступна/пуста → точки отката не будет. В интерактиве введите `PROCEED`, если готовы восстанавливать без отката. |
| «docker-compose в архиве ОТЛИЧАЕТСЯ» | Установлена свежая версия, архив — старый. Выберите «только ДАННЫЕ (база)» — файлы останутся как есть. |
| Импорт БД упал | LAZARUS сам откатит базу из snapshot и поднимет стек. Snapshot сохраняется в каталоге бэкапов (`pre_restore_snapshot_*.sql.gz`) — при провале авто-отката восстановите вручную. |
| «openssl … не поддерживает -pbkdf2» | Старый openssl (< 1.1.0). Обновите openssl на сервере для расшифровки `.enc`-архивов. |
| Восстановление недоступно (SSH-цель) | restore работает только локально — запустите на сервере самой цели. |
