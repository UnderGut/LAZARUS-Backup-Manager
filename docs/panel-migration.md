# Перенос панели на другой сервер

Как переехать с Remnawave Panel на новый сервер с помощью `lazarus migrate panel`.

Перенос выполняется **на НОВОМ сервере** (pull-режим). Старый сервер читается по SSH **только на чтение** (`pg_dump` / `tar`) — панель на нём продолжает работать, пока вы сами не переключите DNS. Откат тривиален: старый сервер не тронут.

---

## TL;DR — 3 шага для новичка

SSH-ключи и S3 **не нужны** — достаточно root-пароля старого сервера.

1. На **новом** сервере установите lazarus (Docker и `docker compose` должны быть запущены):
   ```bash
   curl -sSL https://raw.githubusercontent.com/UnderGut/LAZARUS-Backup-Manager/main/lazarus-backup -o /usr/local/bin/lazarus && chmod +x /usr/local/bin/lazarus
   ```
2. Запустите мастер:
   ```bash
   lazarus migrate panel
   ```
   Введите **IP старого сервера**, **SSH-порт** и выберите **«1 — пароль root»** (ввод скрыт; если нет `sshpass`, мастер предложит его поставить).
3. Пройдите **чеклист переключения** ниже (проверить данные → переключить DNS/ноды → остановить старую панель). **Старый сервер не выключайте**, пока не убедитесь, что новая панель работает.

---

## Как это работает

- **Pull, а не push** — команда запускается на приёмнике и сама тянет данные со старого сервера.
- **Источник read-only** — на старом сервере выполняются только `pg_dump` и `tar`. Ничего не меняется, не останавливается, не удаляется.
- **Полный перенос** — каталог панели (`.env`, compose, сертификаты, nginx) + дамп БД + роли кластера (globals) + infra-billing (если есть).
- **Гарды идентичности** — restore не может попасть в чужой стек (бот/биллинг), а импорт биллинга идёт только в контейнер с ролью billing-БД.
- **Обе раскладки** — официальная установка (docs.remna.st) и eGames (панель + нода на одном сервере) распознаются автоматически.

---

## Предпосылки (новый сервер)

1. Debian/Ubuntu, root, **Docker и `docker compose` установлены и запущены**.
2. `lazarus` установлен (см. [Установку](install.md)).
3. Доступ к старому серверу по SSH: **root-пароль** ИЛИ SSH-ключ. Знать SSH-порт (обычно `22`).
4. Свободный диск: **~3× размера панели** (файлы + БД → архив + распаковка + запас). Мастер проверит и предупредит.

## Пошагово (интерактивный мастер)

```
lazarus migrate panel
```

Мастер спросит по порядку:

```
  Понадобятся всего 3 вещи о старом сервере:
   1. IP-адрес       например 1.2.3.4
   2. SSH-порт       Enter = 22
   3. Пароль root    или путь к SSH-ключу, если вход по паролю отключён

Старый сервер — IP или root@IP (напр. 1.2.3.4): 1.2.3.4
SSH-порт старого сервера (Enter = 22): 22

  Как подключаться к старому серверу?
   1. Пароль root   — проще всего, подходит большинству
   2. SSH-ключ      — если вход по паролю на сервере отключён
  Выбор (Enter = 1): 1
root-пароль старого сервера (ввод скрыт): ********
```

Дальше мастер покажет, **что произойдёт**, и оценку места, и попросит подтверждение:

```
  Что сейчас произойдёт:
  1. Со старого сервера скачается полный бэкап (файлы панели + база данных)
  2. Бэкап проверится и развернётся на ЭТОМ сервере
  3. Вы получите чеклист: что переключить вручную (DNS, ноды, вебхуки)
  Старый сервер не изменится и продолжит работать. Прервать можно в любой момент.

Начать перенос? (y/N): y
```

Если на новом сервере **уже стоит панель**, мастер потребует ввести слово `ПЕРЕНОС` — защита от случайной перезаписи.

### Три способа передать SSH-ключ

Если выбрали «2 — SSH-ключ», ключ можно:
- указать **путь** к приватному ключу (`/root/.ssh/id_ed25519`);
- **вставить ключ целиком** прямо в терминал (мастер попросит вставить и завершить строкой `-----END …`; ключ пишется во временный файл `600` и затирается `shred` на выходе);
- оставить пустым — будет использован ssh-agent / дефолтный ключ.

---

## Вариант для скриптов (флаги)

```bash
lazarus migrate panel --from root@СТАРЫЙ_IP --port 22 --key /root/.ssh/id_ed25519
# --path /opt/remnawave   — если каталог панели на источнике нестандартный
```

| Флаг | Назначение |
|---|---|
| `--from user@host` | старый сервер (можно просто `IP` — пользователь по умолчанию `root`) |
| `--port N` | SSH-порт старого сервера (по умолчанию `22`) |
| `--key /path` | путь к приватному SSH-ключу (для парольного режима не указывать) |
| `--path /opt/remnawave` | каталог панели на источнике, если он нестандартный |

> `migrate panel` работает только интерактивно и несовместим с `--dry-run` (перенос — операторская операция).

## Что именно переносится

| Фаза | Действие | Где |
|---|---|---|
| Preflight | проверка docker/диска локально; SSH, каталог панели, запущенная БД — на источнике | источник read-only |
| Guard | если локальная панель уже есть — перезапись только после слова `ПЕРЕНОС` | локально |
| Pull | полный бэкап: каталог панели + дамп БД + роли (globals) + infra-billing | источник read-only |
| Verify | проверка целостности архива | локально |
| Restore | разворачивание в тот же путь; `.env` панели восстанавливается из архива | локально |
| Post | `docker compose ps` + `pg_isready` | локально |

Имя контейнера БД на источнике определяется автоматически (по compose-метке проекта). Если оно нестандартное и не нашлось — мастер об этом скажет; задайте `PANEL_DB_CONTAINER` в `config.env` и повторите.

## Чеклист переключения (cutover)

Выполнять **вручную и по порядку, ПОСЛЕ проверки новой панели**. Мастер печатает этот же чеклист в конце.

### Проверить
1. Откройте панель на **новом** сервере: пользователи, ноды, подписки, API — всё на месте?

### Переключить
2. **DNS**: домены панели и страниц подписок → IP нового сервера (у Cloudflare учтите proxy-режим и TTL).
3. **Ноды**: в панели все должны стать online (файрвол каждой ноды должен пускать **новый** IP панели).
   - *Если ноды соединяются через overlay-сеть (NetBird/WireGuard)* — подключите новый сервер в overlay; адреса нод в панели менять не нужно (это overlay-адреса нод, а не панели).
   - *Если нода была на одном сервере с панелью (eGames-раскладка)* — DNS её домена → новый IP; проверьте, что панель ходит к ноде по внутреннему адресу docker-шлюза.
4. **Сертификаты**: если выпуск шёл на старом сервере (acme.sh / CertWarden / другой issuer) — перенастройте на новый.
5. **Вебхуки и интеграции**: бот, платёжные callback'и, mini-app, домен биллинга → новый адрес панели.

### Завершить
6. Только когда всё проверено — останавливайте панель на старом сервере: `docker compose down` (не `restart`). Сам сервер не удаляйте хотя бы неделю.
7. Сделайте на новом сервере **тестовый бэкап** (`lazarus` → пункт 1), чтобы убедиться: новый сервер под защитой. См. [Резервное копирование](backup.md).

---

## Откат

Пока вы не переключили DNS — **ничего откатывать не нужно**: старая панель работает как работала. Если новая панель не устроила — просто не переключайте DNS и разберитесь; старый сервер не тронут.

---

## Частые проблемы

| Симптом | Причина / решение |
|---|---|
| «БД панели на источнике не найдена/не запущена» | Нестандартное имя контейнера БД на источнике не нашлось автоматически. Задайте `PANEL_DB_CONTAINER` в `config.env` нового сервера и повторите. |
| «Мало места: нужно ~3× (файлы + БД)» | На новом сервере мало диска. Освободите место или подтвердите на свой риск (гейт — предупреждение, не запрет). |
| Мастер требует `sshpass` | Для входа по паролю нужен пакет `sshpass` — мастер предложит установить (`apt/dnf`). Либо используйте SSH-ключ. |
| Ноды offline после переключения | Файрвол нод не пускает новый IP панели, либо не настроен overlay/DNS ноды. См. пункты 3 чеклиста. |
