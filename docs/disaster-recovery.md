# Аварийное восстановление на чистый сервер

Как поднять Remnawave Panel **с нуля** из готового бэкапа, когда старого сервера уже нет: он умер, его удалил хостер или вы разворачиваете точную копию на новом железе.

Ключевое отличие от [переноса панели](panel-migration.md): здесь у вас **на руках уже есть архив** (лежит в `backup/` или скачан из S3). Ничего с живого источника не тянется — источника может уже не существовать. `lazarus restore` разворачивает архив в пустой каталог: если у нового сервера ещё нет `docker-compose` и `.env`, они **предпосеваются из архива** (bootstrap), и панель поднимается на чистом хосте.

---

## TL;DR — 4 шага для новичка

1. На **новом** сервере поставьте Docker и lazarus:
   ```bash
   curl -sSL https://raw.githubusercontent.com/UnderGut/LAZARUS-Backup-Manager/main/lazarus-backup -o /usr/local/bin/lazarus && chmod +x /usr/local/bin/lazarus
   ```
2. Положите файл бэкапа в каталог `backup/` рядом с lazarus (или настройте S3 и скачайте архив им).
3. Запустите восстановление:
   ```bash
   lazarus restore
   ```
   Выберите **«1 — Полные бэкапы»**, затем нужный архив.
4. Пройдите чеклист переключения ниже (DNS → ноды → сертификаты → вебхуки).

Если у нового сервера **уже стоит панель** (например, вы успели поставить свежую), lazarus заметит расхождение версий и спросит, что делать — см. [«Конфликт версий»](#конфликт-версий).

---

## Два пути — какой ваш

| Ситуация | Что использовать | Гайд |
|---|---|---|
| **А. Сервер умер / ставим с нуля** — есть только архив, живого источника нет | `lazarus restore` из архива | эта страница |
| **Б. Старый сервер жив** — хотим переехать без даунтайма | `lazarus migrate panel` (pull со старого по SSH) | [Перенос панели](panel-migration.md) |

Правило простое: **есть живой источник — `migrate panel`; есть только архив — `restore`.** `migrate panel` внутри тоже делает restore, но сначала сам скачивает свежий дамп со старого сервера. DR стартует уже с готового архива и в источник не ходит.

---

## Предпосылки (новый сервер)

1. Debian/Ubuntu, root, **Docker и `docker compose` установлены и запущены**.
2. `lazarus` установлен (см. [Установку](install.md)).
3. **Файл бэкапа доступен**: лежит в `backup/` локально, либо настроен S3/off-site, откуда его можно скачать.
4. Если архив **зашифрован** — знать `BACKUP_PASSWORD` (при потере пароля расшифровать нельзя).
5. Свободный диск: **~3× размера архива** (сам файл + распаковка + импорт БД).

## Путь А, пошагово: restore на чистый сервер

### 1. Поставить Docker + lazarus

Docker и `docker compose` должны быть **запущены** (`systemctl status docker`). Установка lazarus — командой из TL;DR или через [install.md](install.md).

### 2. Положить архив в `backup/`

lazarus ищет архивы в каталоге `backup/` рядом с собой (переменная `BACKUP_DIR`). Скопируйте туда файл полного бэкапа — имя вида `panel_full_ГГГГММДД-ЧЧММСС.tar.gz` (или `.tar.zst`, или `.enc` для зашифрованного):

```bash
mkdir -p backup
cp /путь/к/panel_full_20260718-030000.tar.gz backup/
```

Из S3/off-site скачать можно средствами lazarus (`lazarus s3 list`, затем загрузить нужный файл вашим клиентом в `backup/`).

### 3. Запустить restore

```bash
lazarus restore
```

Меню восстановления:

```
Восстановление из бэкапа

  1) Полные бэкапы      (файлы + БД)
  2) Бэкапы БД          (только база)
  3) Только файлы
```

Для аварийного развёртывания на чистом сервере выбирайте **1 — Полные бэкапы**: восстановятся и файлы панели (`docker-compose`, `.env`, сертификаты, nginx), и база.

Дальше выберите конкретный архив из списка. lazarus проверит целостность (MAC + формат), покажет план синхронизации (dry-run rsync) и попросит подтверждение перед записью.

### 4. Bootstrap: что происходит на пустом каталоге

Если каталога панели (`/opt/remnawave`) на новом сервере **ещё нет или он пуст** — в нём нет ни одного `docker-compose`. lazarus это распознаёт и **предпосевает `docker-compose` и `.env` прямо из архива**, прежде чем восстановить остальное:

```
Bootstrap: compose/.env предпосеяны в /opt/remnawave из архива (чистый сервер).
```

Без этого шага внутренние гейты (проверка каталога панели, поиск контейнера БД) требовали бы уже установленную панель — и на пустом сервере restore падал бы. Bootstrap решает именно случай «ставим с нуля».

После предпосева lazarus разворачивает файлы, поднимает контейнеры (`docker compose up`) и импортирует дамп БД в поднятый контейнер PostgreSQL.

## Конфликт версий

Частый случай: сервер новый, вы **успели поставить свежую панель** из документации, а архив — со **старой** версии. Тогда `docker-compose` в архиве отличается от установленного. Полное восстановление молча затёрло бы новые файлы старыми (а `rsync --delete` ещё и удалил бы файлы, появившиеся в новой версии).

lazarus это ловит **до записи** и спрашивает (для full-бэкапа с БД):

```
docker-compose в архиве ОТЛИЧАЕТСЯ от установленного на этом сервере.
  Обычная причина: панель установлена или обновлена заново, а архив — со старой версии.
  Полное восстановление затёрло бы новые файлы старыми.

  1) Только ДАННЫЕ (база) — файлы не трогаем (рекомендуется после свежей установки)
  2) Файлы из архива, но СОХРАНИТЬ текущие docker-compose/.env (новые файлы не удаляются)
  3) Вернуть ВСЁ из архива как есть (точная копия старого сервера)
  Выбор (Enter = 1):
```

| Вариант | Что делает | Когда выбирать |
|---|---|---|
| **1. Только данные** | restore переводится в `db_only`: файлы (compose/.env/сертификаты) не трогаются, импортируется только база. | Вы **уже поставили свежую панель** и хотите лишь вернуть данные пользователей/подписок. |
| **2. Сохранить инфру** | Файлы из архива накатываются **без `--delete`**, но текущие `docker-compose` и `.env` **сохраняются** (новые файлы свежей версии не удаляются). | Нужны данные и вспомогательные файлы из архива, но инфраструктуру держим на новой версии. |
| **3. Точная копия** | Возвращается **всё из архива как есть**, включая `.env`. Живые `compose`/`.env` предварительно сохраняются в `backup/infra_replaced_<дата>/`. | Восстанавливаем **бит-в-бит копию** старого сервера; свежую панель откатываем к версии архива. |

> На **чистом** сервере (панели ещё нет) этого вопроса **не будет** — конфликтовать не с чем, отрабатывает bootstrap.

### Важно про `.env` и вариант 3

По умолчанию restore **исключает `.env`** из синхронизации — это защита секретов (живой `.env` с рабочими токенами не перезатирается случайно). Поэтому:

- Варианты **1 и 2** живой `.env` **не трогают**.
- Вариант **3 «точная копия»** обязан вернуть `.env` из архива, иначе копия была бы неполной. lazarus для этого разово снимает exclude (эквивалент флага `--restore-include-env`), предварительно сохранив живой `.env` в `backup/infra_replaced_<дата>/.env`.

Если страховочную копию сделать не удалось (например, диск полон) — lazarus **отменяет** полную замену и молча падает в режим «сохранить инфру», чтобы не затереть живой `.env` без резерва.

Флаг для неинтерактивного режима:

```bash
lazarus --restore-include-env restore   # снять exclude .env вручную (осторожно)
```

## Важно про volume БД

Импорт дампа идёт в **volume PostgreSQL** контейнера панели. Нюансы для чистого сервера:

- На bootstrap-развёртывании volume пуст — импорт проходит чисто.
- Если volume уже содержит данные (панель успела стартовать), перед импортом может понадобиться `DROP SCHEMA` или пересоздание volume. lazarus делает **pre-restore snapshot** текущей БД перед деструктивной операцией — на случай отката.
- Флаги для явного контроля (только когда понимаете последствия):
  ```bash
  lazarus --restore-drop-schema restore    # DROP SCHEMA перед импортом
  lazarus --restore-drop-volume  restore   # удалить volume БД перед восстановлением
  ```
- Имя compose-сервиса БД для поиска volume — `PANEL_DB_SERVICE` (по умолчанию `remnawave-db`). Если оно нестандартное — задайте в `config.env`.

## Чеклист переключения (cutover)

После успешного restore база и файлы на месте, но сервер ещё «невидим» для нод и клиентов. Выполнить **вручную и по порядку**:

### Проверить
1. Откройте панель на новом сервере: пользователи, ноды, подписки, API — всё восстановилось?

### Переключить
2. **DNS**: домены панели и страниц подписок → IP нового сервера (у Cloudflare учтите proxy-режим и TTL).
3. **Ноды**: файрвол каждой ноды должен пускать **новый** IP панели. Если ноды соединяются через overlay (NetBird/WireGuard) — подключите новый сервер в overlay; адреса нод в панели менять не нужно.
4. **Сертификаты**: если выпуск шёл на старом сервере (CertWarden / acme.sh) — перенастройте на новый.
5. **Вебхуки и интеграции**: бот, платёжные callback'и, mini-app → новый адрес панели.

### Завершить
6. Сделайте на новом сервере **тестовый бэкап** (`lazarus` → пункт 1), чтобы убедиться: новый сервер под защитой. См. [Резервное копирование](backup.md).

## Частые проблемы

| Симптом | Причина / решение |
|---|---|
| Restore падает: «каталог панели не найден» | На чистом сервере bootstrap не сработал, потому что в архиве нет `docker-compose`. Убедитесь, что восстанавливаете **полный** архив (пункт 1 меню), а не «только БД». |
| «В архиве нет дампа БД» | Выбрали db_only на архиве только с файлами. Для DR используйте **полный** бэкап. |
| Не расшифровывается архив | Зашифрованный архив без верного `BACKUP_PASSWORD`. Пароль восстановить нельзя — нужен исходный. |
| Спросило про конфликт версий, а сервер должен быть чистым | Панель уже успела развернуться. Выберите **1 (только данные)**, если ставили свежую версию, или **3 (точная копия)**, если нужна копия архива. |
| Ноды offline после переключения | Файрвол нод не пускает новый IP панели, либо overlay не подключён. См. пункт 3 чеклиста. |

## Отличие от «migrate panel» (коротко)

- **DR (`restore`)** — источник данных это **готовый архив**. Живой сервер не нужен и не читается. Подходит, когда сервера уже нет.
- **`migrate panel`** — источник это **живой старый сервер**: lazarus сам снимает с него свежий `pg_dump` + `tar` по SSH (read-only) и разворачивает на новом. Подходит для переезда без потери свежих данных.

Оба сценария в итоге вызывают один и тот же движок восстановления (с bootstrap и гардом конфликта версий) — разница только в том, **откуда берётся архив**.
