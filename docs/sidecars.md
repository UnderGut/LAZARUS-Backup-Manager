# Доп. компоненты: infra-billing, база знаний ИИ-саппорта, доп. пути

Как забэкапить **необязательные базы и каталоги**, которые живут рядом с панелью и ботом: биллинг (`infra-billing`), базу знаний ИИ-саппорта (KB) и произвольные пути вне каталога панели.

Эти компоненты — **сайдкары**: они не входят в основной дамп панели/бота, но lazarus умеет дампить их **в тот же архив**, когда они включены и запущены.

---

## TL;DR — для новичка

1. Откройте меню: `lazarus` → **Настройки** → **раздел 8 «Доп. компоненты»**.
2. Увидите таблицу с двумя строками — **Infra-billing БД** и **KB ИИ-саппорта**. Напротив каждой стоит `✓ ДА` или `✗ НЕТ`.
3. Наберите `1` или `2`, чтобы переключить `ДА ⇄ НЕТ`. `ДА` = бэкапим сайдкар, когда его контейнер запущен.
4. Всё. При следующем бэкапе панели/бота сайдкар попадёт в архив автоматически. Ничего дампить руками не нужно.

Доп. пути (`PANEL_EXTRA_PATHS`) — только через `config.env` (см. ниже), в меню тумблера для них нет.

---

## Что это такое

Три необязательных «довеска» к основным целям бэкапа:

| Компонент | Что это | Куда пишется в бэкапе | К какой цели относится |
|---|---|---|---|
| **infra-billing** | Отдельный `postgres` со **финансовыми** данными биллинга (стек `infra-billing` в каталоге панели) | дамп `billing_*.sql.*` внутри **panel**-архива | панель |
| **KB ИИ-саппорта** | Отдельный `pgvector` с базой знаний (`knowledge`) для ИИ-поддержки бота | дамп `kb_*.sql.*` внутри **bot**-архива | бот |
| **Доп. пути** (`PANEL_EXTRA_PATHS`) | Произвольные **абсолютные** каталоги ВНЕ `PANEL_PATH` (например `certwarden-data`, `configs`) | архив `extra_*.tar` внутри **full/files**-бэкапа панели | панель |

Ключевое отличие от основной цели: сайдкар **необязателен**. Если контейнер не найден или выключен — в режиме `auto` его тихо пропускают, а бэкап панели/бота продолжается штатно.

> Файлы биллинга (`.env-infra-billing`, его `compose`) **уже** входят в files-бэкап панели, потому что физически лежат внутри `PANEL_PATH`. Сайдкар добавляет только **дамп его отдельной БД**.

### Приоритет: панель → бот → сайдкары

Логика вложенности проста: сначала бэкапится **основная цель** (панель и/или бот), и только затем к её архиву доклеиваются относящиеся к ней сайдкары. Если панель не среди целей — биллинг не дампится (некуда). Если бот не среди целей — KB не дампится. В меню это видно прямо в колонке «Идёт в бэкап»: строка гаснет с пометкой `— (панель не бэкапится)` / `— (бот не бэкапится)`.

## Как включить или выключить

Два способа — тумблер в меню (для новичка) и ключи в `config.env` (для эксперта). Они не конфликтуют: тумблер работает **поверх** значения из конфига.

### Способ 1 — тумблер в Настройках (раздел 8)

```
lazarus
  → Настройки
    → 8. Доп. компоненты
```

Экран выглядит так:

```
  Настройки → Доп. компоненты

  Необязательные базы рядом с панелью и ботом — бэкапить их или нет, решаете вы.

   №    Компонент          Контейнер            Бэкапим    Идёт в бэкап
  ────────────────────────────────────────────────────────────────────────
   1.  Infra-billing БД   infra-billing-db     ✓ ДА       панели
   2.  KB ИИ-саппорта     rwp_shop_kb_db       ✓ ДА       бота

  1 / 2 — переключить ДА⇄НЕТ. «ДА» бэкапит, когда контейнер запущен.
```

- `1` → переключить infra-billing `ДА ⇄ НЕТ`.
- `2` → переключить KB `ДА ⇄ НЕТ`.

`✓ ДА` покрывает оба «включённых» режима (`auto` и строгий `true`) — тумблер их не различает и **не затирает** ваш ручной `true`: он лишь переводит между «включено» и `false`.

### Способ 2 — ключи `config.env` (эксперт)

Три состояния для каждого сайдкара:

| Значение | Поведение |
|---|---|
| `auto` (по умолчанию) | контейнер запущен → дампим; выключен/не найден → **тихо пропускаем** |
| `true` | сайдкар **обязателен** — если контейнер недоступен или не прошёл гард, весь бэкап **прерывается** с ошибкой |
| `false` | выключено полностью |

```bash
# infra-billing (сайдкар панели)
PANEL_BILLING_DB_CONTAINER="infra-billing-db"   # пусто = авто-поиск в проекте панели
PANEL_BILLING_BACKUP="auto"                     # auto | true | false

# KB ИИ-саппорта (сайдкар бота)
BOT_KB_DB_CONTAINER="rwp_shop_kb_db"            # пусто = выключить
BOT_KB_BACKUP="auto"                            # auto | true | false
```

> Строгий режим `true` и переопределение имени контейнера — **только** через `config.env`. В меню тумблер оперирует лишь парой «включено ⇄ `false`».

## Что именно дампится

| Сайдкар | Файл в архиве | Источник кредов |
|---|---|---|
| infra-billing | `billing_*.sql.*` | `POSTGRES_USER` / `POSTGRES_DB` из env контейнера биллинга |
| KB ИИ-саппорта | `kb_*.sql.*` | `POSTGRES_USER` / `POSTGRES_DB` из env контейнера KB |
| Доп. пути | `extra_*.tar` | сами каталоги из `PANEL_EXTRA_PATHS` |

Расширение `.sql.*` зависит от компрессии (`gzip` по умолчанию либо `zstd`). Креды сайдкаров **не** нужно прописывать руками — lazarus читает их из `printenv` самого контейнера.

### Identity-гарды (защита от «яда» в архиве)

Сайдкары дампятся не по имени, а по **роли** контейнера — чтобы случайно не сдампить ГЛАВНУЮ БД под чужим именем:

- **billing**: имя или compose-сервис контейнера должны содержать `billing` **и** это должен быть БД-образ. Иначе — гард отключает сайдкар (в `auto`) или прерывает бэкап (в `true`).
- **KB**: контейнер **не должен совпадать** с главной БД бота, панели или биллинга, и должен быть БД-образом. Совпадение = гард, KB-сайдкар отключается.

Это предотвращает сценарий, где `PANEL_BILLING_DB_CONTAINER=remnawave-db` привёл бы к дампу главной БД панели под именем `billing_*` — и отравил бы будущий restore.

## Доп. пути (`PANEL_EXTRA_PATHS`) — подробно

Абсолютные каталоги **вне** `PANEL_PATH`, которые нужно затащить в бэкап панели. Типовой случай — данные CertWarden и внешние конфиги:

```bash
PANEL_EXTRA_PATHS="/opt/certwarden/certwarden-data /var/lib/remnawave/configs"
# разделитель — пробел, ; или ,
```

- Пакуются в отдельный `extra_*.tar` внутри **full** и **files**-бэкапа панели (в db-only не попадают).
- Несуществующий путь при бэкапе — не ошибка: `WARN: путь не найден, пропущен` и идём дальше.

### Безопасность при restore — allowlist

Восстановление доп. путей — **самая осторожная** операция в lazarus, потому что она пишет в системные каталоги вне `PANEL_PATH`. Поэтому:

1. Restore спрашивает отдельно: `Восстановить доп. пути (из PANEL_EXTRA_PATHS) в исходные места? (y/N)` — по умолчанию **нет**.
2. Из архива восстанавливаются **только** пути, перечисленные в **живом** `PANEL_EXTRA_PATHS` (allowlist). Всё, что в архиве есть, но в текущем `PANEL_EXTRA_PATHS` не значится, — **игнорируется**.
3. Распаковка идёт в изолированный STAGE, затем в `/` копируется через `rsync --safe-links` строго по allowlist.

Практическое следствие для **аварийного восстановления на чистом сервере**: если `PANEL_EXTRA_PATHS` там ещё пуст, доп. пути из архива **не** восстановятся:

```
WARN: PANEL_EXTRA_PATHS не задан — доп. пути из архива НЕ восстановлены (0).
      Чтобы восстановить: задайте PANEL_EXTRA_PATHS нужными путями (config.env) и повторите restore.
```

Это сделано намеренно: allowlist — гарантия, что чужой архив не разложит файлы по вашей системе.

## Восстановление сайдкаров (каждый — со своей точкой отката)

При restore архива, где есть сайдкар-дампы, lazarus предлагает импорт **интерактивно и раздельно**. Каждый импорт защищён собственным snapshot-откатом: перед тем как затереть текущую БД, снимается живой снимок, и при сбое импорта БД возвращается на него.

**infra-billing:**

```
WARN: В архиве найден дамп infra-billing — восстановление ПЕРЕЗАПИШЕТ текущую БД биллинга (infra-billing-db).
```

Импорт проходит только если целевой контейнер прошёл role-гард (роль `billing-db`). Иначе — `ГАРД: … не billing-db — импорт биллинга ОТКЛОНЁН.`

**KB ИИ-саппорта:**

```
WARN: В архиве найден дамп KB — восстановление ПЕРЕЗАПИШЕТ текущую БД KB (rwp_shop_kb_db).
```

Импорт отклоняется, если целевой контейнер пуст, совпадает с главной БД (бот/панель/billing), не БД-образ или принадлежит чужому compose-проекту.

Порядок безопасности при импорте каждого сайдкара:
1. `pg_isready` — цель жива?
2. snapshot текущей БД (точка отката);
3. `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` + импорт дампа;
4. при ошибке — авто-откат на snapshot.

Подробнее про интерактивный restore и точки отката — в [Восстановлении из бэкапа](restore.md).

## Частые вопросы

| Симптом | Причина / решение |
|---|---|
| `billing`/`KB` не попал в бэкап, хотя тумблер `ДА` | Контейнер сайдкара не запущен. В `auto` это штатный тихий пропуск. Запустите контейнер либо, если он обязателен, поставьте `PANEL_BILLING_BACKUP=true` / `BOT_KB_BACKUP=true`. |
| `ГАРД: … не billing-db … Sidecar отключён` | Имя в `PANEL_BILLING_DB_CONTAINER` указывает не на billing-БД. Имя/сервис должны содержать `billing`. |
| `BOT_KB_BACKUP=true, но бот удалённый (ssh) — KB-sidecar не поддержан` | KB-сайдкар работает только для локального бота. |
| Строка сайдкара в меню серая: `— (панель/бот не бэкапится)` | Соответствующая основная цель не выбрана. Сайдкар доклеивается только к своей цели (панель→billing, бот→KB). |
| Доп. пути не восстановились (`0`) | На целевом сервере `PANEL_EXTRA_PATHS` пуст — allowlist не разрешил. Задайте пути в `config.env` и повторите restore. |
