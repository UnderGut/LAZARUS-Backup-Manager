# Резервное копирование

Как создать бэкап **Remnawave Panel** (или Telegram-бота) с помощью `lazarus`. Панель — основная цель; бот поддерживается как дополнительная или альтернативная.

Бэкап читает данные **только на чтение** — панель/бот продолжают работать. Дамп БД (`pg_dump`) + архив каталога (`tar`) сжимаются и (при заданной парольной фразе) шифруются, после чего кладутся в `BACKUP_DIR` и по желанию уходят в облако / Telegram.

---

## TL;DR — 3 шага для новичка

1. Запустите меню:
   ```bash
   lazarus
   ```
2. Выберите пункт **1 — Создать бэкап**, затем **1 — Полный бэкап** (БД + файлы).
3. Дождитесь `SUCCESS`. Готовый архив лежит в `BACKUP_DIR` (по умолчанию `/opt/lazarus-backup/backup`) с именем вида `lazarus_panel_full_2026-07-19_14_30_00.tar.zst`.

Из cron/скрипта то же самое одной командой:
```bash
lazarus --yes backup create
```

---

## Четыре типа бэкапа

| Тип | Что входит | Меню | CLI (длинно) | CLI (коротко) | cron-алиас |
|---|---|---|---|---|---|
| **Полный** | БД **+** файлы каталога (+ сайдкары) | `1` | `backup create` / `backup full` | `-B -c` | `backup_full` |
| **Только база данных** | дамп БД (+ роли/сайдкары), файлы не входят | `2` | `backup db` | `-B -d` | `backup_db` |
| **Только файлы** | каталог без базы данных | `3` | `backup files` | `-B -f` | `backup_files` |
| **Incremental** | только изменения с последнего полного | — | `backup inc` | `-B -i` | — |

> Полный — рекомендуемый вариант: один архив, из которого восстанавливается всё. Incremental всегда опирается на предыдущий `full` (см. ниже).

## Из меню

```bash
lazarus
```
Пункт **1 — Создать бэкап** открывает подменю (`menu_manual_backup`):

```
Создание бэкапа

Цель: Remnawave Panel  (/opt/remnawave)

 1. Полный бэкап          — база данных + файлы  ← рекомендуется
 2. Только база данных    — быстро, файлы не входят
 3. Только файлы          — без базы данных
 0. Назад

Выбор (Enter — назад):
```

После создания появится пост-бэкап-меню: посмотреть **топ-5 крупных файлов в архиве**, список **пропущенных файлов** и, если облако не настроено, — предложение настроить копию в облако (S3 / FTP / WebDAV).

## Из командной строки

Длинные и короткие формы эквивалентны, работают в интерактиве и в cron:

```bash
lazarus backup create        # полный (алиас: backup full, -B -c)
lazarus backup db            # только БД (-B -d)
lazarus backup files         # только файлы (-B -f)
lazarus backup inc           # incremental (-B -i)
lazarus backup list          # список существующих бэкапов (-B -l)
```

Глобальные флаги ставятся **перед** командой:

```bash
lazarus --yes backup db          # cron: без вопросов
lazarus --debug backup create    # подробный лог
lazarus --dry-run backup create  # предпросмотр без записи
```

Для cron доступны и «плоские» алиасы (их прописывает планировщик lazarus): `lazarus backup_full`, `lazarus backup_db`, `lazarus backup_files`. См. [Автоматизация и расписание](automation.md).

## Цель бэкапа: панель, бот или обе

Что бэкапить, задают ключи в `config.env`:

| Ключ | Значение | Смысл |
|---|---|---|
| `BACKUP_TARGET` | `panel` \| `bot` | Основная (первичная) цель. |
| `BACKUP_SECONDARY` | `panel` \| `bot` \| пусто | Вторая цель — бэкапится **тем же прогоном**. Пусто = одна цель. |

Пример: `BACKUP_TARGET=panel` + `BACKUP_SECONDARY=bot` → одна команда `lazarus backup create` снимет **обе** цели за проход. Меню и дашборд ведёт первичная цель; вторую трогает только диспетчер.

Архивы двух целей не путаются, потому что у них разные префиксы имён:

| Цель | Префикс архива |
|---|---|
| Панель | `lazarus_panel_*` |
| Бот | `lazarus_*` |

Сменить цель можно в **Настройках → Цель бэкапа**. Панель и бот могут быть локальными или удалёнными (по SSH) независимо — стриминговый бэкап по SSH описан в [Переносе панели](panel-migration.md) и настраивается там же.

## Что входит в полный бэкап

Полный бэкап панели собирает в один архив:

- **каталог панели** (`PANEL_PATH`, по умолчанию `/opt/remnawave`) — `.env`, compose-файлы, сертификаты, nginx-конфиги;
- **дамп базы данных** панели (`pg_dump`);
- **роли кластера** — `pg_dumpall --globals-only` (владельцы/гранты), сайдкар `globals_*`;
- **сайдкары** (если активны):
  - `infra-billing` — отдельная БД биллинга, дамп `billing_*` (ключи `PANEL_BILLING_DB_CONTAINER` / `PANEL_BILLING_BACKUP`);
  - доп. пути вне каталога панели — `PANEL_EXTRA_PATHS` (сайдкар `extra_*`).

Для бота полный бэкап аналогично собирает каталог бота + дамп его БД + сайдкар KB (`rwp_shop_kb_db`, ключи `BOT_KB_DB_CONTAINER` / `BOT_KB_BACKUP`).

Подробно про сайдкары — [Дополнительные компоненты](sidecars.md).

## Формат имён файлов

```
<префикс>_<тип>_<timestamp>[__v<версия>].tar.<ext>[.enc]
```

- **префикс** — `lazarus_panel` для панели, `lazarus` для бота;
- **тип** — `full` / `db` / `files` / `inc`;
- **timestamp** — `YYYY-MM-DD_HH_MM_SS`;
- **ext** — `zst` (zstd) или `gz` (gzip);
- **`.enc`** — если задана парольная фраза шифрования.

Примеры:

```
lazarus_panel_full_2026-07-19_14_30_00.tar.zst.enc     # полный бэкап панели, зашифрован
lazarus_panel_db_2026-07-19_02_00_00.tar.gz            # только БД панели
lazarus_files_2026-07-19_03_00_00.tar.zst              # только файлы бота
lazarus_inc_2026-07-19_06_00_00__base_2026-07-19_02_00_00.tar.zst
```

Incremental несёт в имени `__base_<timestamp>` — метку полного бэкапа, от которого он считает изменения. При восстановлении lazarus по этой метке сам находит нужный `*_full_<base>` в `BACKUP_DIR`. Поэтому базовый полный бэкап **нельзя удалять**, пока живы его инкременты.

## Пропущенные файлы

При файловом (и полном) бэкапе крупные файлы **исключаются** из архива, чтобы не раздувать его: порог задаёт `MAX_FILE_SIZE_MB` (по умолчанию `1` МБ; `0` = без лимита). Дополнительно исключаются каталоги из `EXCLUDE_DIRS` (логи, кэши и т.п.).

Пропущенные при последнем бэкапе файлы всегда сохраняются в `BACKUP_DIR/.last_skipped.txt`. Посмотреть:

```bash
lazarus skipped
```

или пункт **«Пропущенные файлы»** в пост-бэкап-меню. Причина указывается для каждого (`size > MAX_FILE_SIZE_MB=1MB`, исключённый каталог и т.д.). Если что-то большое обязано попасть в бэкап — поднимите `MAX_FILE_SIZE_MB` или добавьте путь в `PANEL_EXTRA_PATHS`.

> База данных под этот лимит **не попадает** — дамп БД архивируется всегда целиком.

## Проверка результата

```bash
lazarus backup list      # что уже создано (по типам и целям)
lazarus verify           # проверить integrity всех архивов (MAC + распаковка)
```

Полезно после первого бэкапа на новом сервере — убедиться, что архив читается и не повреждён.
